# ffplay-standalone

Build upstream [ffplay](https://github.com/FFmpeg/FFmpeg/blob/master/fftools/ffplay.c)
unmodified against prebuilt FFmpeg shared libraries — no FFmpeg compilation.
One project, two platforms, one provider: **BtbN's daily GPL-shared builds**
(`win64` / `linux64`), with CMake + MSVC on Windows and CMake + GCC on
Linux.

The vendored sources under `fftools/` are byte-identical upstream snapshots; all
local adaptation lives in `shim/` and the generated `config.h`.

## Layout

| Path | What it is |
|------|------------|
| `fftools/` | Pristine upstream snapshot, synced by script — never hand-edit |
| `shim/` | Headers the prebuilt package does not install (`compat/`, `libavutil/`), regenerated by script |
| `cmake output` | `config.h` generated from the prebuilt tree (version / configuration / CC_IDENT) |
| `scripts/update.py` | Cross-platform (Python 3.12+): refresh prebuilt package + sync fftools + regenerate shim |
| `UPSTREAM.toml` | Snapshot identity and the single version knob (per-platform assets) |
| `config.h.in` | Template for the generated config |

## Build

Windows (VS2022, x64; `winget install Python.Python.3.12` once for the update script):

```powershell
py scripts\update.py
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

Linux (`apt install build-essential cmake ninja-build libsdl2-dev`):

```bash
python3 scripts/update.py
cmake -B build -G Ninja
cmake --build build
```

Output: `build/Release/ffplay.exe` (+ DLLs) resp. `build/ffplay` (+ `.so` via
`$ORIGIN` rpath). First update downloads the prebuilt package (~90 MB) and the
SDL2 dev zip (Windows only) into `third_party/` (cached, gitignored). CMake
build dirs are platform-specific — when one checkout is shared between Windows
and WSL, configure them into separate directories (e.g. `build/` and
`build-linux/`).

## Tracking upstream

Alignment policy: **the fftools ref always equals the source commit of the
prebuilt package in use**. BtbN rebuilds every variant from the same commit
each day, so running `update.py` on both platforms back-to-back keeps both
platforms on one commit — that is what makes the twin comparison below
meaningful on each platform and across platforms. The prebuilt tree is the
authority: when its commit differs from the manifest, the script re-fetches
the rolling `latest` asset and moves the manifest to it.

Provenance comes from the package itself (`ffversion.h` carries a
git-describe version); abbreviated hashes are expanded via the GitHub API.
Source snapshots are always GitHub archives of the exact recorded commit.
Deliberate deviations (e.g. pulling an ffplay.c fix from a release branch
ahead of the package) go into `[sync] fftools_ref` with a `reason` in
`UPSTREAM.toml`. `.gitattributes` pins `* -text` so vendored files round-trip
byte-exact.

## Twin verification

The prebuilt packages ship their own `ffplay` binaries. Because ours is built
from the same fftools commit against the same libraries, `ffplay -version`
must be byte-identical to the package's — and it is, on both platforms. Any
difference localizes to the config shim or the compiler, which is exactly the
risk surface of a shim-heavy setup.

## Why the generated config.h

ffplay prints the `configuration:` line compiled into itself, while the
libraries report their own; `opt_common.c` warns when they differ. The probe
runs the package's own `ffplay -version` at configure time and lifts
`FFMPEG_VERSION`, `configuration:` and `built with` verbatim into `config.h`,
so the banner matches the package exactly. Remaining macros follow the BtbN
GPL build (GPLv3, all libav*, `CONFIG_LIBPLACEBO=0` which makes
`ffplay_renderer.c` compile as a stub — see the known trade-off in
`UPSTREAM.toml` history / `shim/` comments).
