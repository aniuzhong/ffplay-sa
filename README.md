# ffplay-standalone

Build upstream [ffplay](https://github.com/FFmpeg/FFmpeg/blob/master/fftools/ffplay.c)
unmodified against [gyan.dev](https://www.gyan.dev/ffmpeg/builds/) prebuilt FFmpeg
shared libraries with CMake + MSVC. No FFmpeg compilation involved.

The vendored sources under `fftools/` are byte-identical upstream snapshots; all
local adaptation lives in `shim/` and the generated `config.h`.

## Layout

| Path | What it is |
|------|------------|
| `fftools/` | Pristine upstream snapshot, synced by script — never hand-edit |
| `shim/` | Headers gyan does not install (`compat/`, `libavutil/`), regenerated by script |
| `cmake output` | `config.h` generated from the gyan tree (version / configuration / CC_IDENT) |
| `scripts/update-gyan.ps1` | Fetch latest (or pinned) gyan release, record its source commit |
| `scripts/sync-fftools.ps1` | Copy fftools snapshot + regenerate shim at that commit |
| `UPSTREAM.toml` | Snapshot identity and the single version knob (gyan + sdl2 versions) |
| `config.h.in` | Template for the generated config |

## Build

```powershell
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

Output: `build\Release\ffplay.exe` with the gyan + SDL2 DLLs copied next to it.
First configure downloads `ffmpeg-<ver>-full_build-shared.zip` (~100 MB) and the
SDL2 VC dev zip into `third_party\` (cached, gitignored).

## Tracking upstream and gyan

Alignment policy: **the fftools ref always equals the source commit declared by
the gyan package in use** (its `README.txt` lists `Source Code: .../commit/<hash>`).
The pair moves together — release builds for stability, gyan's daily git-master
builds for chasing ffplay.c master. This guarantees API/ABI compatibility
without judgment calls and keeps our exe a behavioural twin of gyan's own
`ffplay.exe` (identical `-version` banner), so any difference localizes to the
config shim or the compiler.

Workflow:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\update-gyan.ps1   # [-Version 9.1]
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\sync-fftools.ps1  # [-SourceDir <ffmpeg-tree>]
cmake --build build --config Release
```

Sync is fully network-based, no local FFmpeg checkout required: gyan release
builds pull the official `ffmpeg.org` source tarball (cross-checked against the
declared commit via `git ls-remote`, falling back to a GitHub archive of the
exact commit on mismatch), while git-master builds archive the exact commit
directly — release tarballs only exist per tag. `sync-fftools.ps1` copies the
fftools whitelist, then regenerates `shim/` as the closure of the `compat/…` /
`libavutil/…` headers the snapshot actually includes. Pass `-SourceDir` to sync
from an existing checkout instead. Deliberate deviations (e.g. pulling an
ffplay.c fix from a release branch ahead of gyan) go into `[sync] fftools_ref`
with a `reason` in `UPSTREAM.toml`. `.gitattributes` pins `* -text` so vendored
files round-trip byte-exact.

## Why the generated config.h

ffplay.exe prints the `configuration:` line compiled into itself, while the DLLs
report their own; `opt_common.c` warns when they differ. The probe runs the
gyan tree's own `ffplay.exe -version` at configure time and lifts `FFMPEG_VERSION`,
`configuration:` and `built with` verbatim into `config.h`, so the banner matches
gyan exactly. Remaining macros follow gyan full_build (GPLv3, all libav*, SDL2,
`CONFIG_LIBPLACEBO=0` which makes `ffplay_renderer.c` compile as a stub).
